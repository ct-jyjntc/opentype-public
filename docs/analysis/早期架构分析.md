# 早期架构分析报告

分析对象：`/Applications/目标应用`（v2.8.1 build 130，bundle id `now.desktop.app`）
产出目标：提取产品架构、协议与关键参数。

## 1. 技术栈与整体架构

应用是 Electron 外壳 + Swift 原生 helper 的混合体，529MB，arm64。

```
目标应用/Contents/
├── MacOS/目标应用                    Electron 主程序
└── Resources/
    ├── app.asar                      JS 主体（11157 个文件，未压缩仅索引）
    │   ├── dist/main/index.js        主进程 635KB（obfuscator.io 混淆）
    │   ├── dist/preload/index.mjs    桥接层 11KB（混淆）
    │   ├── dist/renderer/            渲染层（Vite 构建，1 个主 chunk 7.6MB）
    │   └── node_modules/             全量依赖
    ├── lib/                          4 个 Swift 编译的 dylib
    │   ├── input-helper/libInputHelper.dylib        文本注入
    │   ├── keyboard-helper/libKeyboardHelper.dylib  全局按键监听
    │   ├── context-helper/libContextHelper.dylib    前台上下文采集
    │   └── util-helper/libUtilHelper.dylib          权限/设备/系统状态
    └── drizzle/                      14 个 SQL 迁移文件
```

关键依赖（来自 `package.json`）：`koffi`（FFI 调 Swift 库）、`better-sqlite3` + `drizzle-orm`（本地库）、`electron-store`（配置）、`electron-updater`（热更新，源 `desktop-app-static.com/desktop-release/`）、`@sentry/electron`（错误上报）。

**架构要点**：JS 层不做任何原生能力硬编码，全部通过 `koffi` 以 C ABI 调用 Swift 库。这是该应用能同时支持 macOS/Windows 的原因——JS 逻辑共享，原生能力按平台替换 dylib/dll。

## 2. 混淆与还原

`dist/main/index.js` 与 `preload/index.mjs` 使用 obfuscator.io 的 string-array 混淆：字符串统一存放在一个巨型数组函数中，通过轮转 IIFE 打乱顺序，再由解码函数按索引取用。

还原方法（脚本见 `scripts/` 同类思路）：
1. 提取体积最大的空参函数体（字符串数组），体积次大的单参函数体（解码器）
2. 执行头部轮转 IIFE，使数组顺序就位
3. 收集 `alias = decoder` 形式的别名映射（共 63 个）
4. 正则替换 `alias(0x...)` 为解码后的字符串字面量

结果：**9518 处字符串引用全部还原，0 处残留**。渲染层未做字符串数组混淆，但使用变量名混淆，可读性依赖语义推断。

## 3. 核心流程

### 3.1 录音触发

不使用 Electron `globalShortcut`。原因明确：`globalShortcut` 只能响应按下、拿不到松开，无法实现按住说话（push-to-talk），且会独占按键吞掉用户在其他应用的正常使用。

实际方案：`libKeyboardHelper` 用 `CGEventTap`（`cgSessionEventTap` + `headInsertEventTap` + `listenOnly`）监听全局 keyDown/keyUp，把事件序列化成 JSON 回调给 JS。JS 侧做热键匹配与防抖。

`listenOnly` 选项很关键——只监听不拦截，绝不吞掉用户按键。

### 3.2 音频采集与编码

| 参数 | 值 | 来源 |
|---|---|---|
| 采样率 | 16000 Hz (`0x7d00`) | 渲染层 `SAMPLE_RATE` |
| 声道 | 1（单声道） | `CHANNEL_COUNT` |
| 位深 | 16 | `SAMPLE_SIZE` |
| 采集缓冲 | 4096 帧 | `PROCESSOR_BUFFER_SIZE` |
| 编码格式 | Opus / Ogg | `libopusenc.dylib` |
| 码率 | 32000 bps (`0x7d00`) | `opus_convert_advanced` 参数 |
| 帧长 | 20 ms (`0x14`) | 同上 |
| 压缩复杂度 | 10 | `libopuschunk_session_set_complexity` |

采集侧用 `AudioContext` + `createScriptProcessor(4096, 1, 1)`，而非 `MediaRecorder`——后者产出 webm 容器，服务端还需解容器才能拿到裸 Opus，且无法控制采样率。

`libopuschunk` 是自研的分块会话库，提供 `session_start` / `session_encode_wav_chunk` / `session_set_complexity` / `session_destroy`，支持边录边编码（流式），不必等录音结束再整段压。

### 3.3 上传协议

`POST https://api.desktop-app.com/ai/voice_flow`，`multipart/form-data`：

| 字段 | 说明 |
|---|---|
| `audio_id` | 记录 UUID |
| `mode` | `voice_transcript` / `voice_command` / `voice_translation` |
| `audio_file` | Opus 数据，文件名 `<audioId>.ogg`，MIME `audio/ogg` |
| `audio_metadata` | JSON，含 `audio_duration` 等 |
| `audio_context` | JSON，**加密后**上传（见 3.4） |
| `parameters` | JSON，模式专属：`selected_text` 或 `output_language` |
| `duration` / `is_retry` / `user_over_time` / `send_time` / `device_name` | 辅助字段 |

超时 40 秒（`0x28 * 0x3e8`）。响应体：
- 正常：`{status:'OK', data:{refine_text, delivery, user_prompt, web_metadata, external_action, raw_text}}`
- 配额耗尽：`{important_notification: ...}` → 前端走付费引导而非报错

`delivery` 字段决定后续动作：`external` 表示由服务端驱动外部动作（如发邮件、发推），此时客户端不注入文本。

### 3.4 上下文加密

请求中间件对特定字段做混合加密（`encryptValue`）：

```
1. 随机生成 32 字节 AES 密钥 + 16 字节 IV
2. RSA-OAEP(SHA-256) 加密该 AES 密钥 → _key
3. AES-256-GCM 加密明文 → 密文 + authTag 拼接 → _data
4. 输出 {_encrypted:true, _v:1, _type:'json'|'str', _key, _data} 全 base64
```

RSA 公钥由服务端下发（`rsa:get-config`），客户端可配置开关。

### 3.5 上下文采集

`libContextHelper` 走 macOS Accessibility API：

- `getFocusedInputInfo` — 焦点元素 → 逐层向上找 `AXTextArea`/`AXTextField`（最多 12 层），取 `AXValue`、`AXSelectedText`
- `collectContentBefore/After` — 从光标位置前后收集文本（最多 20 层，带超时）
- `findWebInfoByTraversingUp` — 向上找 `AXWebArea`，取 URL 与标题
- `isBrowserApp` — 按 bundle id 判断浏览器
- `smartJoinTexts` — 智能拼接收集到的文本片段

服务端另下发域名黑名单（`/app/get_blacklist_domain`），命中则不上传上下文——密码框、银行页面这类场景。

### 3.6 文本注入

`libInputHelper` 的方案是**剪贴板 + 模拟 Cmd+V**，而非逐字符 CGEvent：

- `savePasteboard` / `restorePasteboard` — 存档并还原用户剪贴板
- `insertText` / `insertRichText`（带 HTML）— 写入剪贴板后发 Cmd+V
- `getSelectedText` / `getSelectedTextBySimulateCopyAsync` — 模拟 Cmd+C 读选区
- `deleteBackward` — 用于「回退 AI 润色」
- `findKeyCodeForCharacter` — 键码映射

**为什么不用逐字符注入**：中文输入法环境下 IME 会拦截并乱序重排合成事件，剪贴板粘贴是唯一在 Chromium/Electron/原生 App/终端里都稳定的方案。

### 3.7 认证

标准 OAuth2 + PKCE：

- `createAppLoginUrl` 生成 `code_verifier`（随机 hex）→ `code_challenge`（SHA256 后 base64url）
- 登录页 `https://www.desktop-app.com/login/app/auth?code_challenge=...&state=...&next=/login/google|email|apple|sso`
- 回调换取 token：`POST /oauth/exchange_app_login_code`
- 刷新：`POST /oauth/refresh_access_token`（**不携带旧 token**，否则过期 token 会导致刷新也失败）
- 中间件 `目标应用RequestAuthMiddleware` 统一注入 `Authorization: Bearer <token>`

`userData` 用 `electron-store` 持久化，密钥由 PBKDF2 派生（10000 轮，SHA-256，salt 为设备指纹 + 应用名）。

### 3.8 本地数据模型

SQLite（`desktop-app.db`）+ drizzle，14 个迁移文件演进。最终 `history_v2` 表结构要点：

- 文本：`refined_text`（润色稿）
- 音频：`audio_local_path`、`audio_metadata`、`mic_device`、`mic_device_info`
- 上下文：`focused_app_name` / `bundle_id` / `window_title` / `web_title` / `web_domain` / `web_url`
- 模式：`mode`、`mode_meta`（blob）
- 同步三件套：`sync_status`、`sync_attempt_count`、`server_updated_at`、`synced_from_cloud`
- 索引：7 个复合索引，其中同步候选集用**部分索引**（partial index）只覆盖有效记录：

```sql
CREATE INDEX idx_history_v2_push_candidate_v2 ON history_v2
  (user_id, sync_status, created_at, sync_attempt_count)
  WHERE status = 'completed'
    AND ((refined_text IS NOT NULL AND refined_text <> '')
      OR (mode = 'voice_command' AND json_extract(mode_meta, '$.ai_result.delivery') = 'external'));
```

这条 SQL 透露了产品判断：**只有真正产生了价值的记录才值得同步**——纯空转写和未外发的命令都不推。

### 3.9 同步引擎

`SyncEngine` 按 channel 管理任务，含防抖推送、定时 `sync/check`、增量分页（游标 `{createdAt, id}`）、失败标记与指数退避。多账号隔离通过 `isCurrentOwnerUserId` 校验，切换用户时中断在途任务。

## 4. 值得借鉴的设计决策

| 决策 | 理由 |
|---|---|
| 剪贴板注入而非逐字符 | 兼容 IME、Electron、终端，唯一稳定方案 |
| CGEventTap listenOnly | 既能拿到 keyUp，又不干扰用户按键 |
| 上下文先采、浮窗后现 | 浮窗一旦出现就抢焦点，顺序反了上下文就丢了 |
| 16kHz 单声道 + Opus 32kbps | 语音识别足够，带宽约为 WAV 的 1/12 |
| 分块流式编码 | 边录边压，松开热键后几乎无编码等待 |
| 混合加密上下文 | RSA 传密钥 + AES 传数据，兼顾安全与性能 |
| 同步候选用部分索引 | 从数据层杜绝无效同步流量 |
| 域名黑名单 | 密码框/银行页面主动放弃上下文采集 |
| `delivery: external` 分支 | 服务端可驱动外部动作，客户端不重复注入 |
| 独立原生 helper 库 | JS 逻辑跨平台共享，原生能力按平台替换 |

## 5. 实现对应

见 `voxtype/` 目录。已实现并通过测试的部分：

- 4 个 Swift 原生 helper（C ABI 导出，koffi 可加载）
- 热键状态机（push-to-talk + toggle + 防抖 + 取消）
- 音频采集（16kHz 单声道）与 Opus/WAV 编码（含无编码库时的回退）
- 语音主链路编排（上下文采集 → 录音 → 编码 → 上传 → 注入 → 落库）
- 本地数据层（drizzle + better-sqlite3，WAL 模式）
- IPC 桥接（白名单式 contextBridge）
- 浮窗与主界面

未实现（需要服务端配合）：真实 ASR 后端、账号体系、云端同步服务端、上下文加密的公钥分发。
