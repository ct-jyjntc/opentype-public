# 主进程协议分析报告

分析对象：`/Applications/目标应用` v2.8.1 (build 130)，bundle id `now.desktop.app`，arm64，529MB
分析方法：asar 解包 → obfuscator.io 字符串数组还原 → 字符窗口检索 → 逐模块精读
产出：完整协议、参数、架构决策

---

## 1. 混淆还原方法与成果

主进程 `dist/main/index.js`（608KB 单行）与 preload 使用 obfuscator.io 的 string-array 混淆。

**还原流程**：
1. 定位体积最大的空参函数（字符串数组，56631 字符）与单参解码函数
2. 执行头部轮转 IIFE，使数组顺序就位
3. 收集 `alias = decoder` 别名映射（63 个）
4. 正则替换 `alias(0x...)` 为解码后的字符串字面量

**成果：9518 处字符串引用全部还原，0 残留。**

**关键工程教训**：还原后的文件仍是**单行** 608KB，且含 SVG path / base64 超长行（单行可达 18KB）。裸 `grep` / `rg` 会输出整行，一次匹配即产生几十万字符。必须用**按字符偏移输出固定窗口**的检索方式，而非按行检索。

## 3. 核心协议

### 3.1 语音上传 `POST /ai/voice_flow`

`multipart/form-data`，超时 40 秒（`0x28 * 0x3e8`）。

| 字段 | 内容 |
|---|---|
| `audio_id` | 记录 UUID |
| `mode` | **`transcript` / `ask_anything` / `translation`**（注意：不是本地枚举值） |
| `audio_file` | Opus 数据，文件名 `<audioId>.ogg`，MIME `audio/ogg` |
| `audio_metadata` | JSON，含 `audio_duration` |
| `audio_context` | JSON，**加密后**上传 |
| `parameters` | JSON，模式专属 |
| `duration` / `is_retry` / `user_over_time` / `send_time` / `device_name` | 辅助字段 |

**本地枚举 → 服务端值的映射**（`wc` 映射表）：
```js
{
  [VOICE_TRANSCRIPT]:   'transcript',
  [VOICE_COMMAND]:      'ask_anything',   // ← 关键：本地叫 command，服务端叫 ask_anything
  [VOICE_TRANSLATION]:  'translation'
}
```

**`parameters` 按模式构造**：
- `voice_command` → `{selected_text}`（来自 `mode_meta.selected_text`）
- `voice_translation` → `{output_language}`（用户选择 或 `mode_meta.output_language`）
- `voice_transcript` → 空对象

**响应结构**：
```js
// 成功
{status:'OK', data:{refine_text, raw_text, delivery, user_prompt, web_metadata, external_action}, debug}
// 配额耗尽
{important_notification: ...}   // → 前端走付费引导，非错误
// 失败
{detail, code}
```

### 3.2 音频编码参数

| 参数 | 值 | 出处 |
|---|---|---|
| 采样率 | 16000 Hz (`0x7d00`) | 渲染层 `SAMPLE_RATE` |
| 声道 | 1 | `channels` |
| 位深 | 16 | `SAMPLE_SIZE` |
| 采集缓冲 | 4096 帧 | `PROCESSOR_BUFFER_SIZE` |
| 码率 | 32000 bps (`0x7d00`) | opusWorker `d.bitrate` |
| 帧长 | 20 ms (`0x14`) | `d.frameSize` |
| VBR | true | `d.vbr` |
| 信号类型 | `auto` | `d.signal` |
| 复杂度 | 10 | `setComplexity` |

**opusWorker 消息协议**：
```js
// 主线程 → worker
{taskId, method: 'processBufferToOgg', args: [...]}
// worker → 主线程
{taskId, success: true, result: {...}}
{taskId, success: false, error: string}
```

**编码降级链**（关键可靠性设计）：
1. Buffer 模式（`opus_convert_buffer` + `opus_estimate_output_size`）——最快，无需临时文件
2. 遇错误码 `-5`（buffer too small）→ **缓冲翻倍重试**，最多 `bufferRetryCount` 次
3. Buffer 模式彻底失败 → **文件模式**（`opus_convert_advanced`，写临时 wav 再读 ogg）

**chunkSessionWorker 消息协议**（流式）：
```js
{taskId, method: 'continuousEncodingSessionStart' | 'continuousEncodingSessionEncode' | 'continuousEncodingSessionEnd', args}
```
底层调用 `libopuschunk_session_create` / `_set_complexity` / `_encode_wav_chunk` / `_destroy`，支持边录边编码，松开热键后几乎无编码等待。

### 3.3 数据加密（RSA + AES 混合）

**公钥来源**：服务端下发。`GET /user/get_user_info` → `data.rsa_public_key`，拿到即 `enabled = true`。

**加密算法**（`rsaAesEncrypt`）：
```
1. AES 密钥 = randomBytes(32)                        // dp = 0x20
2. IV = Buffer.alloc(12, 0)                          // hp = 12 字节全零 ⚠️
3. _key = RSA-OAEP(SHA-256)(AES密钥, 公钥) → base64
4. 密文 = AES-256-GCM(明文, AES密钥, IV)
5. _data = base64(密文 ‖ authTag)
6. 输出 {_encrypted:true, _v:1, _type:'str'|'json', _key, _data}
```

**⚠️ 重大安全发现：加密失败时降级明文发送**

```js
encryptValue(value, opts) {
  if (value == null || isEncrypted(value) || isAlreadyPlain(value)) return value
  const fallback = opts.fallback ?? true      // ← 默认 true
  // ... 尝试加密 ...
  if (hasUsableKey()) {
    try { return await this.rsaAesEncrypt(value, this.publicKey) }
    catch { /* 记录错误，继续往下走 */ }
  }
  // 加密不可用或失败 → 回退明文
  let result = value
  if (fallback) result = stringify(value)     // 明文 JSON
  this.trackEncryptionFailure({reason, fallback_used: ...})
  return result
}
```

失败原因分类：`missing_public_key` / `userinfo_fetch_failed` / `node_crypto_error` / `unknown_error`。

**含义**：公钥获取失败（如 `get_user_info` 接口异常）时，用户的输入框上下文会**明文上传**。用户对「上下文已加密」的预期与实际不符。

### 3.4 凭据存储

两条独立的 PBKDF2 密钥派生路径（10000 轮，SHA-256，32 字节输出）：

```js
// 现行：userData 加密
generateEncryptionKey() {
  const platform = os.platform(), arch = os.arch()
  const salt0 = sha256(platform + '-' + arch)      // hex
  return pbkdf2Sync(salt0 + app.getName(), 'desktop-app-user-service', 10000, 32, 'sha256')
}

// 迁移用：读取旧版 electron-store 数据
migrateKey() {
  const salt0 = sha256(hostname + '-' + platform + '-' + arch + '-' + userInfo().username)
  return pbkdf2Sync(salt0 + app.getName(), 'electron-user-service', 10000, 32, 'sha256')
}
```

**安全评估**：密钥完全由**公开可推导的机器特征**（platform/arch/appName）决定，不涉及用户秘密。任何能在该机器上执行的代码都可重新推导出同一密钥并解密 `user-data.json`。这不是「加密存储」，而是「混淆存储」——它能防住随意翻看文件的人，防不住本地攻击者。

### 3.5 认证流程（OAuth2 + PKCE）

```
1. code_verifier  = randomUUID() + randomUUID() 拼接（hex 字符串）
   code_challenge = base64url(sha256(code_verifier))
   state          = randomUUID()
2. 登录页 URL：
   https://www.desktop-app.com/login/app/auth
     ?code_challenge=<challenge>&state=<state>&next=/login/google|email|apple|sso|login
3. pendingAppLogin = {state, codeVerifier}   // 内存暂存
4. 回调 → POST /oauth/exchange_app_login_code（校验 state）
5. 刷新 → POST /oauth/refresh_access_token（不携带旧 token）
```

`next` 路径映射：`google→/login/google`、`email→/login/email`、`apple→/login/apple`、`sso→/login/sso`、`login→/login`。

请求中间件 `目标应用RequestAuthMiddleware` 统一注入 `Authorization: Bearer <token>`，跳过列表含 `/oauth/refresh_access_token`、`/get_blacklist_domain`。

## 7. 本地数据模型

### 7.1 schema 演进（14 个迁移）

`history` 表 → **`history_v2` 重建**。重建而非 ALTER 的原因：drizzle 迁移 0003 有一次 `DROP COLUMN`（`audio_cloud_path`），且字段类型变更（`mode_meta` 从 text 改 blob）在 SQLite 的 ALTER 限制下难以完成，重建更干净。

`history_v2` 最终结构（26 列）：
```sql
id, user_id, status, mode, refined_text, duration, created_at, updated_at,
audio_local_path, audio_metadata, app_version, mic_device, mic_device_info,
client_metadata, mode_meta, debug_info, audio_context,
server_updated_at, sync_status, sync_attempt_count, synced_from_cloud
```

字段语义推断：
- `mode_meta` (blob) —— 模式附加数据：`{selected_text?, output_language?, ai_result?: {delivery}}`
- `client_metadata` (blob) —— 客户端环境快照
- `mic_device_info` (blob) —— 麦克风设备详情（label、groupId 等）
- `audio_context` (text) —— 加密后的上下文 JSON
- `debug_info` (text) —— 调试信息（错误详情等）

### 7.2 同步候选集（最有价值的设计）

```sql
CREATE INDEX idx_history_v2_push_candidate_v2 ON history_v2
  (user_id, sync_status, created_at, sync_attempt_count)
  WHERE status = 'completed'
    AND ((refined_text IS NOT NULL AND refined_text <> '')
      OR (mode = 'voice_command' AND json_extract(mode_meta, '$.ai_result.delivery') = 'external'));
```

**这条 SQL 编码了产品判断**：只有真正产生价值的记录才值得同步——
- 已成功转写**且**文本非空，**或**
- 是语音命令**且**服务端返回了 `delivery: 'external'`（即触发了外部动作）

空转写、失败记录、未外发的命令都不推。用**部分索引**（partial index）从数据层杜绝无效同步流量，而非在应用层过滤。

### 7.3 同步引擎参数

| 参数 | 值 | 含义 |
|---|---|---|
| `mo` | 3 | `sync_failed` 状态的最大重试次数 |
| `Dg` | 200 (`0xc8`) | 单批推送记录数 |
| `Og` | 50 (`0x32`) | 游标分页大小 |
| `pushDebounceMs` | 10000 | 本地变更后防抖推送延迟 |
| `syncCheckTriggers` | `['appStarted','userLoggedIn']` | 检查时机 |
| `syncCheckIntervalMs` | undefined | 该 channel 不定时轮询 |

**SyncEngine 结构**（`class sn`）：
```js
tasksByChannel: Map           // channel → task
pushDebounceTimers: Map       // 防抖计时器
syncCheckIntervalTimers: Map  // 定时检查
checkingChannels: Set         // 正在检查
pushingChannels: Set          // 正在推送
sessionGeneration: number     // 会话代际
```

**多账号隔离机制**（值得照抄）：
```js
invalidateSession() {
  this.sessionGeneration += 1        // 代际递增
  this.pushDebounceTimers.forEach(clearTimeout)
  this.pushDebounceTimers.clear()
}
isCurrentSession(gen) { return gen === this.sessionGeneration }
```
所有异步流程在关键节点检查 `isCurrentSession`，账号切换时递增代际，在途任务自动失效。这比「手动取消所有 Promise」更可靠。

## 12. 值得照抄的设计决策

| 决策 | 理由 |
|---|---|
| 剪贴板注入而非逐字符 | 兼容 IME、Electron、终端，唯一稳定方案 |
| CGEventTap + 原生 ShortcutDetector | 原生侧判定「按住时长/按键次数」，能拿到 keyUp 且不干扰用户按键 |
| 上下文先采、浮窗后现 | 浮窗一旦出现就抢焦点，顺序反了上下文就丢了 |
| 16kHz 单声道 + Opus 32kbps | 语音识别足够，带宽约为 WAV 的 1/12 |
| 流式分块编码（libopuschunk） | 边录边压，松开热键后几乎无编码等待 |
| 编码三级降级 | Buffer → 缓冲翻倍重试 → 文件模式，最大化成功率 |
| 同步候选用部分索引 | 从数据层杜绝无效同步流量 |
| sessionGeneration 代际隔离 | 账号切换时在途任务自动失效，比手动取消可靠 |
| 域名黑名单服务端可下发 | 发现新敏感站点无需发版即可覆盖 |
| 独立权限检查子进程 | 绕过 TCC 缓存，拿实时权限状态 |
| 六窗口拆分 | 浮窗/侧栏/卡片/主界面独立，各自最小化资源与权限 |
| `delivery:'external'` 协议 | 服务端可驱动外部动作，客户端不重复注入 |

## 13. 发现的安全问题

1. **加密失败降级明文**（高危）：`fallback` 默认 true，公钥获取失败时上下文明文上传，与用户「已加密」的预期不符。
2. **AES-GCM 使用全零 IV**（中危）：12 字节固定零 IV，同一密钥下多次加密会泄露明文异或关系。虽然每次都用新随机密钥，实际风险被缓解，但这是明确的密码学误用。
3. **凭据密钥可推导**（中危）：PBKDF2 的 salt 完全由公开机器特征构成，本地攻击者可重新推导密钥解密 `user-data.json`。
4. **`__DEV_API_HOST` 可重定向 API**（中危）：配置项允许把 API 指向任意主机（非 desktop-app.com 域名时 `isDev=true`）。若可被写入，则构成凭据劫持路径。
5. **`page:open-devtools` 通道存在**（低危）：生产构建中仍注册，需确认是否受环境判断保护。
