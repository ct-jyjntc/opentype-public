# 原生层分析报告

对象：`/Applications/目标应用/Contents/Resources/lib/` 下 6 个原生库
方法：`lipo` 取 arm64 切片 → `nm`/`strings` 符号与常量提取 → radare2 `aa` + `pdc` 二进制分析
结论：**未 strip，符号表完整保留**，业务逻辑可还原到接近源码语义

### 3.2 二进制分析证据：smartJoinTexts 的拼接规则

伪代码显示核心循环（`pdc` 输出，已化简）：

```c
// 对 textElements 数组逐项遍历
for (i = 0; i < count; i++) {
    (text, isText) = elements[i]          // 元组 (String, Bool)
    trimmed = text.trimmingCharacters(in: .whitespacesAndNewlines)
    if (trimmed.isEmpty) continue          // 空串直接跳过

    if (lastIsText && isText) {            // 前一项与当前项都是正文
        result.append(text)                // 直接拼接，无分隔符
        lastIsText = true
    } else {
        result.append("\n")                // 0xa = 换行
        result.append(text)
    }
}
```

**还原的规则**：
- 用 `CharacterSet.whitespacesAndNewlines` 判空，纯空白项被丢弃
- **相邻的两项若 `isText` 均为 true，直接拼接不插分隔符**（处理被 AX 树切碎的同一句话）
- 其余情况插入 `\n`（`0xa`，从 `mov w8, 0xa` 指令确认）

这解释了为什么采集到的上下文是「连贯段落」而非「碎片列表」——`isText` 标志区分
正文节点与结构节点，前者被合并。

### 3.6 bottomUpURLTraversalWhitelist（已动态提取）

该常量是**运行时构造**的：`pdc` 显示它走 `swift_once` 惰性初始化，
变量位于 `__DATA,__common`（未初始化段），静态文件内容为全零，`dlsym` 也拿不到
（local 符号）。**静态分析到此为止，必须动态提取。**

**提取方法**（已实测成功）：
1. `dlopen` 加载 dylib，拿到 image slide
2. 按 `slide + 0xae3c` 计算访问器地址（local 符号，需手工算偏移）
3. 调用访问器触发 `swift_once` → `swift_initStaticObject` 填充 `__common`
4. 解析返回的 `Swift.Array<String>`：`buf[2]` 是 count，元素从 `buf[4]` 起每项 16 字节
5. 每个元素是 Swift String 的两字布局：`w0` 低 48 位是长度，`w1` 低 48 位是数据指针

**实测结果（2 项）**：
```
bottomUpURLTraversalWhitelist:
  [0] len=16  "org.chromium.Chromium"
  [1] len=21  "com.apple.Safari"
```

**语义修正**：上一轮推断为「向上遍历时信任的站点白名单」，实际是
**「需要向上遍历 DOM 查找 URL 的浏览器 bundle id 列表」**。

反汇编证据（`getFocusedAppInfoSync` @ `0x467c`）：
```asm
bl  bottomUpURLTraversalWhitelist      ; 取白名单
ldr x2, [x0]                           ; 数组 count
bl  Array<String>.contains             ; 判断当前应用 bundleId 是否在表内
tbz w20, 0, 0x47a8                     ; 不在表内 → 跳过 URL 遍历
bl  AXUIElementCreateApplication       ; 在表内 → 创建应用级 AX 元素
bl  findWebInfoByTraversingUp          ; 向上遍历找 URL 与标题
```

即：**只有 Chromium 与 Safari 才走「向上遍历 DOM 找 URL」这条较重的路径**，
其余浏览器（Chrome/Firefox/Edge/Brave 等）用更轻量的方式获取 URL。
这与 `isBrowserApp`（13 个浏览器前缀）是两个不同粒度的判定——
前者决定「是不是浏览器」，后者决定「是否需要特殊遍历」。

### 5.3 热键判定机制（二进制分析确认）

`isShortcutMatch` 的伪代码显示它访问 `letterKeys` 集合（`swift_once` 惰性初始化）
与 `targetShortcuts`，逻辑为：

```c
// 简化后的判定流程
if (pressingKeycodes.isEmpty) return false
for (target in targetShortcuts) {              // 每个目标是 Set<String>
    if (pressingKeycodes.count not in allowedCounts) continue
    if (target == Set(pressingKeycodes.map(toName))) return true
}
return false
```

**`allowedCounts: Set<Int>` 是关键**：它限制了「按下的键数」必须落在允许集合内。
这解释了为什么同一主键能区分单击/双击/按住——不同交互模式对应不同的
`pressingKeycodes.count`。

`getKeyPressDuration(keyCode:)` 提供按住时长，是 push-to-talk 判定的基础。

### 5.4 监听器自愈机制

```
Restarting watcher with new interval: 
watcherTimer / isRestarting / watcherResults
processEvents()
```

`KeyboardMonitor` 持有一个 `NSTimer`（`watcherTimer`）周期性调用 `processEvents()`，
并用 `watcherResults: [Int32: Bool]` 记录每个键的 tap 是否仍有效。
`isRestarting` 防止重入。

**为什么需要这个机制**：macOS 在以下情况会**静默禁用** event tap——
辅助功能权限被撤销、系统睡眠唤醒、目标进程无响应超时（`kCGEventTapDisabledByTimeout`）。
`CGEventTap` 被禁用后不会再收到任何事件，且不会报错。
必须周期性检查并重新启用，否则表现为「热键突然失灵」。

JS 侧对应埋点 `performance_monitoring_keyboard_monitor_restart_triggered` 印证了这一点。

### 5.5 虚拟键盘识别


识别 Karabiner（键盘改键工具）创建的**虚拟 HID 键盘**，并区分内建键盘

## 6. util-helper：设备指纹与系统状态

### 6.1 设备指纹：Keychain + 本地缓存双写自愈

从字符串还原的完整状态机：

```

"Both Keychain and cache are missing, generating new Device ID..."

"Device ID not found in Keychain"
"Keychain read failed, status code: "
"Keychain read failed, attempting to recover from local cache..."

"Keychain self-healing failed, but still using cached value"
"Local cache updated to Keychain value"

"Keychain write failed, status code: "

"New Device ID saved to Keychain, but local cache save failed"
"New Device ID saved to local cache, but Keychain save failed"
"New Device ID save failed (both Keychain and cache failed), using temporary value"
"Unable to delete old value from Keychain, status code: "
"Invalid UUID format in Keychain: " / "Invalid UUID format in cache file: "
"Attempting to save invalid UUID format to Keychain: " / "to file: "
"Failed to convert UUID to Data"
"Unable to locate Application Support directory"
```

对应函数：`getUUIDFromKeychain()` / `getUUIDFromFile()` / `saveUUIDToKeychain(_:)` /
`saveUUIDToFile(_:)` / `getCacheFileURL()`

**完整算法还原**：
1. 读 Keychain → 成功则同时更新本地缓存（`Local cache updated to Keychain value`）
2. Keychain 失败 → 回退读本地缓存文件 → 成功则**反向自愈 Keychain**
3. 两者都缺 → 生成新 UUID → 双写
4. 任一写入失败 → 用另一处兜底
5. 双写都失败 → 用临时值（不崩溃）

**设计意图**：macOS 的 Keychain 在应用签名变化、系统升级、用户切换后会失效。
纯 Keychain 方案会导致用户「设备 ID 变化」→ 服务端视为新设备 → 配额重置或风控误判。
双写 + 自愈保证了 ID 的稳定性。

**隐私含义**：这是一个**随机 UUID**（`UUID` 类型，非硬件序列号），
不像 JS 侧的 PBKDF2 那样依赖机器特征。`getDeviceId` 的伪代码显示它调用
`DeviceIdentifier.getId()`，是纯软件标识——**不可从硬件推导**，这一点比
JS 侧的密钥派生更注重隐私。

### 7.2 opus_convert_advanced 二进制分析

伪代码显示其调用链：
```c

                          int* out_error, float* out_bitrate)

    ...

```

内部函数 `_opus_parse_wav` 确认了输入格式是 **WAV**（与 JS 侧「文件模式」一致）。

### 7.3 内嵌完整编解码器

`nm` 输出显示两个库都内嵌了完整的 Opus/CELT 实现：
```
_celt_encoder_init / _celt_decode_with_ec / _celt_lpc / _celt_autocorr
_alg_quant / _alg_unquant / _anti_collapse / _bitexact_cos / _bitexact_log2tan
_analysis_compute_dense / _analysis_compute_gru    ← 神经网络 VAD
```
**静态链接**（无外部 libopus 依赖），且包含 DRED（深度冗余解码）相关符号
（`_celt_decode_with_ec_dred`）——这是 Opus 1.4+ 的抗丢包特性。
